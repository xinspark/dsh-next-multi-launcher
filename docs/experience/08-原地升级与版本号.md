# 08 · 原地升级后版本号还停在旧版

## 症状

DSH-NEXT 用安装包原地升级到 `2.0.22-next` 后，启动器版本页仍然写着：

```
已登记版本
2.0.21-next   内核 0.2.2-rc.1   E:\FXS\APP\DSH NEXT
```

同一屏上，实例行的第二行却已经是 `DSH-NEXT 2.0.22-next · 内核 0.2.2-rc.1`；
「在线下载」里 `v2.0.22-next` 一行没有「已安装」，反倒给 `v2.0.21-next` 挂上了。

## 根因

登记的目录名就是版本号：`versions\<tag>` 是一条指向安装目录的 junction，
`tag` 在**登记那一刻**从 `app.asar!/package.json.version` 读出后写死在目录名里。

原地升级只换掉了链接**目标**里的内容，目录名不会变。之后：

- `scan()` 用目录名当 `tag`（`inspect_dir(dir, tag)` 的第一个参数），`shell_version` 才读 asar
  → 版本页显示 `tag`，于是显示旧号；
- 实例文件的 `version` 字段也存的是旧 tag；
- 「已安装」徽标拿在线 tag 和登记 tag 比对 → 新版对不上、旧版反倒对上。

## 证据

```text
PS> Get-ChildItem E:\FXS\APP\DSH-NUL\versions | Select Name,LinkType,Target
Name        LinkType Target
2.0.21-next Junction E:\FXS\APP\DSH NEXT      # 目标里已经是 2.0.22-next

PS> node -e "…openAsar('E:/FXS/APP/DSH NEXT/resources/app.asar')…"
version 2.0.22-next   dependencies['@deepseek-ai/dsh'] 0.2.2-rc.1
```

即：链接名 = 2.0.21-next，链接目标里的 asar = 2.0.22-next。

## 结论

启动时做一次幂等对账（`versions.rs::reconcile`，在 `build_state` 里调用）：

1. 只处理 `is_link` 的登记——真实目录是用户的安装树，不擅自改名；
2. `shell_version != tag` 时把链接 `rename` 成真实版本号；
3. 引用旧 tag 的实例文件一并改到新 tag；
4. 目标版本号已存在登记就跳过，绝不合并两棵安装树。

回归：`versions::tests::reconcile_renames_link_and_remaps_instances`（建 junction → 改写目标 asar
→ 断言改名、实例改引用、二次调用幂等）与 `reconcile_leaves_real_directory_alone`。
